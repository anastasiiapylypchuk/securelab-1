## 2. Змінений маршрут

HTTP-запит із JSON -> десеріалізація у безпечний DTO CreateIncidentRequest (без системних полів) -> серверна валідація у Lab02Endpoints.cs (MapPost) -> перевірка на активний дублікат 
через db.Incidents.AnyAsync -> створення сутності Incident із серверними значеннями статусу та власника -> збереження через db.SaveChangesAsync() -> відповідь 201 Created.

HTTP-запит із параметрами q та sortBy -> екранування метасимволів (%, _, \) у Lab02Endpoints.cs (MapGet) -> передача патерну в параметризований LINQ-запит 
через EF.Functions.ILike -> фільтрація sortBy через серверний allowlist (оператор switch) -> отримання даних ToListAsync() -> відповідь 200 OK.

## 3. Виконані зміни

`Реалізовано серверну валідацію для POST /api/incidents, тобто перевірка обов'язкових полів, лімітів довжини (160 для title, 4000 для description), валідація enum (IncidentSeverity), 
контроль часу (occurredAtUtc), cross-field перевірка (довжина опису для критичних інцидентів) та перевірка логіки (title != description).

Додано перевірку на наявність активних дублікатів за заголовком (повертає 409 Conflict).

Усунуто SQL-ін'єкцію в GET /api/incidents/search вразливу конкатенацію рядків у FromSqlRaw замінено на параметризовані запити за допомогою LINQ (EF.Functions.ILike).

Додано екранування символів % та _ для запобігання логічним маніпуляціям пошуку.

Впроваджено жорсткий allowlist для параметра sortBy

Додано інтеграційні тести для перевірки валідації DTO, логіки дублікатів та відсутності витоку даних при спробі SQL-ін'єкції.`

## 5. Security-сценарій

##Гіпотеза
Локальний endpoint пошуку отримує недовірені дані через q та sortBy. Існує ризик, що ці значення увійдуть до SQL-структури запиту.

##Стан до
У вразливому коміті a2b944bf529021fb597d5a6fa6003e04b53db00b у файлі Lab02Endpoints.cs SQL-запит збирався шляхом прямої конкатенації: var sql = "SELECT * 
FROM incidents WHERE title ILIKE '%" + (q ?? "") + "%'...".

##Мінімальний PoC
До параметра пошуку передано payload: zz-no-match' OR TRUE --.

##Спостереження
Апостроф достроково закрив текстовий рядок, OR TRUE зробило умову істинною для всіх рядків, а -- відкинуло ліміти. СУБД повернула всі наявні в базі інциденти (18 записів).

##Першопричина
Користувацький ввід безпосередньо з’єднувався з текстом SQL-команди до її виконання рушієм бази даних.

##Виправлення
Використано параметризацію через LINQ (EF.Functions.ILike), де дані передаються окремо з екрануванням метасимволів. Для sortBy реалізовано allowlist (оператор switch).

##Позитивна регресія
Повторне введення PoC більше не змінює логіку (повертається порожній масив). Легітимні запити з апострофами обробляються успішно без помилки 500.

##Залишковий ризик
Виправлення захищає лише від ін'єкцій у цьому конкретному ендпоінті. Воно не вирішує питань відсутності авторизації (перегляд чужих інцидентів) чи пагінації.

## 6. Висновок

Першопричину SQL-ін'єкції успішно усунуто за допомогою переходу на параметризовані запити EF Core (LINQ) та застосування жорсткого allowlist для структури сортування. 
Впроваджено надійну серверну валідацію DTO при створенні ресурсів, що блокує некоректні дані, дублікати та маніпуляції з бізнес-логікою. Усі регресійні та security-тести успішно 
пройдено, що підтверджує надійність механізмів захисту та відповідність контракту API вимогам безпеки.
